This recount fits no tokenizer; the 2026-10-20 count of 26,328,493 tokens covered only the header-licensed subset.

Extrapolating that ordered-prefix policy to **64,000,000,000 raw text bytes** yields **12,636,682,776 tokens**, or **12,573,499,362 after a 0.5% validation reserve**, excluding BOS; the 2026-10-20 forecast was **1,685,023,171 / 1,676,598,055**. This is a conditional forecast from one shard's ordered prefix, not a full-source token count or a guarantee of unique usable tokens. Under it, each model's Python target fits inside the 59 available StarCoderData Python containers: the selected S rehearsal's 0.9B tokens need **4.58GB** of raw Python text from **5** containers, the optional larger S target of 1.8B needs **9.16GB** from **9**, M's 4.5B needs **22.91GB** from **22**, and L's 8.1B needs **41.23GB** from **40**. Before the recovery, the optional larger S target, M and L exceeded the source (**66, 164 and 295** containers needed of 59). No new source, repeat epoch or rights relaxation is assumed beyond the owner's D-05 correction for ISC and Unlicense. The small rehearsal's full build still waits for review.

Two caveats bound this forecast. A license mapping exists only for the **209,914** sampled files; a full build first needs an owner-authorized metadata read for every container it uses, and the forecast assumes the join keeps the sample's match rate there. The 64GB source size is the plan's approximation; 59 Python containers at the container-0 text proxy of 1,049,067,107 bytes each come to about **61.9GB**, which would lower the token figures by about 3%.
