# Post-training run worker

`tools/posttrain_run.py` runs post-training run 1 on one A40 Pod that already exists: a generation probe, ARC-Easy, evaluation generation of the base and SFT checkpoints, one SFT pass and RL screening generation. For run 2 it runs `Run2Worker` (`tools/posttrain_run2.py`), the same worker with RL and the more-SFT control, whose rewards and dev verdicts come from the Mac through the [reward bridge](rl-bridge.md), then ARC-Easy and evaluation generation of both selected checkpoints. It never creates, rents or deletes a machine. Every artifact leaves through R2 as soon as it exists; the Mac's supervisor verifies all of them before the Pod may be deleted. Hidden tests never reach the Pod. Operations are in [post-training runs](../posttrain-runs.md) and the runbooks for [run 1](../../POSTTRAIN_RUNBOOK.md) and [run 2](../../POSTTRAIN_RUN2_RUNBOOK.md).

## Worked example

**The smoke.** `python -m tools.posttrain_run smoke --output runs/posttrain-smoke` writes tiny fixtures and runs all seven stages on CPU into an in-memory bucket in about three seconds. The model has 1 layer, width 32 and a 192-token context; the tokenizer is a byte-level BPE with 96 merges trained on text like the fixtures' (`smoke_tokenizer`), so a prompt like `Write add_11(x) returning x + 11.` plus its public test is 24 chat-v1 tokens (61 with no merges). With 3 pool tasks per split and the protocol cap of 512, each pool attempt may generate `min(512, 192 - 24) = 168` tokens. A greedy file has 3 attempts and an n = 8 file 24.

**The limits of run 1.** The ceiling is $3.00 at $0.60 an hour. `ceiling_limits(3.00, 0.60)` gives the wall `floor(3.00 x 3600 / 0.60) = 18,000 s`, the timer `18,000 - 180 = 17,820 s`, the worker's cost stop $3.00 and the watchdog's $2.99. A Pod whose create request went out at `ORIGIN` has its timer armed for `ORIGIN + 17,820`.

**The launch plan.** At the planning rates: the probe 360 s; ARC on three parents `3 x (20 + 54) = 222 s`; base evaluation `7 x 20` s of loads plus `(2 x 2,000 x 9 x 512 + 705 x 256) / 5,000 = 3,722.5 s` of generation, 3,862.5 s; SFT `20 + 120 + 106 x 32,768 / 56,765 + 4 x 827,850 / 94,862 + 4 x 5 = 256 s`; ARC on the SFT weights 74 s; SFT evaluation 3,898.6 s (the chat benchmarks cap at 512); screening `20 + 1,000 x 8 x 256 / 5,000 = 429.6 s`; and the 900 s reserve. That is 10,003 s, so the worker launches only if that much of the 17,820 s is left.

**The SFT plan.** 3,390 rows at 32 per update is `ceil(3,390 / 32) = 106` updates, the last with 30 real rows and 2 rows of padding. Warmup is `round(0.03 x 106) = 3` updates. Dev loss is measured at `round(k x 106 / 4)` for k = 1, 2, 3, that is updates 26, 53 and 80 (Python rounds 26.5 to 26 and 79.5 to 80), and at 106.

**Run 2's bounds.** `posttrain_ops.bridge_timeouts` derives every bound on one bridge wait from the reward channel's rules. One try of a program is at most its budget plus the host's slack: the longest budget is a 100-case I/O task's, `2 + 0.25 x 100 = 27 s`, so `27 + 15 = 42 s`. A reward attempt may take 4 tries with 1, 2 and 4 s between them: `4 x 42 + 7 = 175 s`. The Mac's 8 workers take 256 attempts in `ceil(256 / 8) = 32` rounds: `32 x 175 = 5,600 s`, the Mac's `--reward-timeout`. A dev check is 200 tasks x (8 samples + 1 greedy) = 1,800 programs in 225 rounds of 42 s, plus 42 s for a program still running: `9,492 s`, the Mac's `--dev-timeout`. The bridge adds a 2 s Mac poll, a listing, a read and a write over SSH each tried 5 times to its 30, 120 and 120 s timeout, `3 x (1 + 2 + 4 + 8) = 45 s` of backoff and a 0.5 s Pod poll: `2 + 5 x 270 + 45 + 0.5 = 1,397.5 s`. So the Pod waits up to 6,997.5 s for rewards and 10,889.5 s for a dev check, the Mac watchdog lets an idle GPU wait 60 s longer than that while the heartbeat reads `awaiting_rewards`, and the worker keeps 10,889.5 s ($1.81) free before every update.

**A dead Mac, second by second.** The worker sends dev check 0 at `t = 0`. The Mac's server renews its lease at `t = 2, 4, ...` and, while it reads, scores or answers a request, from its progress ticker. Each look at the inbox (every 0.5 s) checks the wait every 5 s: a lease renewed within its 60 s becomes the heartbeat's `progress_unix`. The Mac dies at `t = 300`, just after a renewal. From then on `progress_unix` stays at 300: the in-Pod timer would delete the Pod at `300 + 900 = 1,200`. The worker does not wait for that: at `300 + 600 = 900` it gives the wait up (`bridge_lost`, a reward-wait stop for `run_rl`), which saves the weights, and the run finalizes in full, its weights and `report.json` in R2, before the timer fires.

**The margin.** Say 1,550 s of spend is left before the cost stop. Dev check 0, whose wait is bounded by its timeout, may start only if that timeout fits; before update 1 `should_stop` asks whether one full wait, the longer kind, fits. In the smoke's scale (a 1,523.5 s dev timeout, a 1,572.5 s margin) the check runs and the run then stops with `wait_margin`: a wait that cannot end before the cost stop never starts, because nothing interrupts it once it has.

**The projected finish.** The rule runs before every stage. Say the probe measures 7,000 tok/s at batch 64 and eval-base is about to start at 1,800 s. The work remaining is eval-base `140 + 18,612,480 / 7,000 = 2,799 s`, SFT 256 s, ARC 74 s, eval-sft 2,825 s, screening 313 s and the 900 s reserve: 7,167 s, ending at 8,967 s, inside the 17,820 s. The stage starts. Had the probe measured 2,500 tok/s, it would already have stopped the run. If eval-base then takes 4,000 s, its files' cap-priced rate, `18,612,480 / (4,000 - 140) = 4,822` tok/s, replaces 7,000 in the projection before SFT; and a stage still generating at `17,820 - 900 = 16,920 s` stops there, leaving the reserve to the finalization.

## Data flow and shapes

1. **Launch gates (`run`).** The receipt must be `pilot_readiness_receipt posttrain`'s, for run 1, bound to this specification, binding and preflight by SHA-256; every gate `true`; the policy no weaker than the ceiling-derived limits (`check_policy`); the armed deadline no later than the policy's billing origin plus the 17,820 s timer lifetime (so the 180 s margin inside the wall holds); the timer live, not a dry run, with its idle rule watching this worker's heartbeat (`check_self_destruct`); the R2 prefix this Pod's. The binding must name exactly the specification's inputs (`posttrain_binding.require_specification`), every input is re-hashed (`verify`), and the shipped revision must equal the receipt's.
2. **The worker's store.** `GuardedStore` wraps the R2 store: any request but GET and HEAD whose key is not under `posttrain-runs/1/<pod id>/` raises `PrefixViolation` before a socket opens. The uploader, the round trip and the final checks all use it.
3. **Each stage.** `run_stage` checks the wall, cost and idle limits, applies the projected-finish rule, runs `run_<kind>` and records its seconds and outputs (each output as soon as it is exported, so a stopped stage still lists what it left in R2). During GPU work `tick` refreshes the heartbeat's `last_gpu_activity_unix` and progress counter and stops at the wall or the cost stop, or at the finalization reserve 900 s before the lifetime's end (`finalization_reserve`, which finalizes in full). After each evaluation file `observe_generation` re-bases the projections on the files' cap-priced rate when it is below the probe's.
   - `probe`: `[B, 256]` prompts of random tokens at the chosen lengths through `benchmark_generation`, one call per batch size.
   - `arc`: `evaluate_choices` with the project's label-likelihood scorer, float32, a tick every 64 questions.
   - `eval`: `generate_completions` with `ticking_generate`, which is `generate_many` batch for batch (prompts sorted longest first, cut into batches of 64) with a tick after each `[64, <=1024]` batch.
   - `sft`: an `SFTLoader` of `[16, 1024]` inputs and targets, two microbatches per update, through the `Trainer` with `loss_normalization: update_targets`; `assistant_loss` over each dev set at the quarter checks; `save_weights` for each new lowest.
   - `screen`: `screening_rollouts` on chunks of 64 candidates (`64 x 8 = 512` rows in batches of 64), then `write_attempts` with the header.
   - `rl` (run 2): the SFT weights through `load_weights` with fused attention; `run_rl` with a `WorkerRewards` around `BridgeRewardSource` (256 attempts a request) and a `BridgeDevEvaluator` whose `WorkerDevExecutor` sends each check's programs (up to 1,800); `should_stop` is the worker's (limits and the margin), `on_check` exports each check's `checkpoint.pt` as `rl-check-<update>`, and `facts` are the Mac's. The client's sleep is `wait_sleep`, which heartbeats `awaiting_rewards` and reads the lease.
   - `more-sft` (run 2): `run_more_sft` with RL's busy seconds as its budget, RL's update-0 check as its start, RL's attention kernel, the same evaluator and `should_stop`, each check exported as `more-sft-check-<step>`.
4. **Artifacts.** `export_label` publishes `exports/<label>/` with its files and `record.json`, lists every file in `report["artifacts"]` with its key, SHA-256 and size, and submits the label to the uploader as a milestone. Nothing is rolled or pruned.
5. **Finalization** is the pretraining rehearsal worker's (`Worker.finalize`), reused through two hooks: `transfer_window_seconds` and `closing_record`. The heartbeat's `r2_final` is `{report_key, report_sha256, artifact_count}`. The supervisor downloads the report pinned to that SHA-256 and HEADs every listed artifact. Run 2's `before_finalize` first closes the bridge client and exports the bridge directories as `bridge` (`bridge.tar`, regular files only, bounded).

## Design choices and common mistakes

- **Why a ceiling, not a wall.** A dead Mac must not let a Pod run to the pretraining rehearsal's $10: the timer, the watchdog and the worker all stop within $3.00 of spend. Deriving all three from one function keeps them from drifting apart.
- **Why an in-Pod idle rule.** The Mac watchdog's idle rule needs the Mac. The in-Pod timer's needs only the Pod: 900 s with no GPU work and no progress stamp deletes it. The bootstrap stamps progress after every step, so a slow but live setup is not idle; a worker's rewritten heartbeat is not activity unless its GPU timestamp or `progress_unix` moves.
- **Why every stage stops instead of skipping.** A stop leaves every artifact made so far in R2 and a report naming the reason; the owner re-prices. Skipping a stage would silently change what run 2 starts from.
- **Why the cached encoder.** The reference `ByteBPE.encode` applies all 65,000 merges to every chunk: about a second per pool prompt and a third of a second per ARC question with the real tokenizer, so encoding 2,000 prompts before the first batch would idle the GPU past the 600 s limit. Every prompt path (the probe, ARC, `generate_completions`, screening) uses `FastEncoder`, whose IDs are the reference's exactly, in about a millisecond a prompt; the tests disable the reference encoder while the worker runs.
- **Why weights only.** SFT's selected checkpoint feeds evaluation, screening and run 2, all of which start fresh optimizers, so the optimizer state (two thirds of a full checkpoint) is never needed.
- **A common mistake** is running `eval-execute` on the Pod export: its placeholders would fail every attempt. The executor refuses an export, and refuses a full file whose export differs from the one the completions name.
- **Why derived bounds, not 420 s.** A flat timeout either stops a run whose Mac is merely slow or waits far longer than any real wait. The bounds follow from the channel's own budgets, tries and workers and the bridge's SSH rules, in one function the specification, the policy and the runbook all read, so they cannot drift apart.
- **Why the lease, not the worker's own heartbeat.** During a wait the worker is alive but its GPU is idle; its own stamps would prove only that it is waiting. The Mac renews `server.lease` on the Pod only while a server is polling or reading, scoring or answering a request, and dates it with the Pod's clock, so a fresh lease proves a live Mac and a stale one lets the in-Pod idle rule fire. It counts only during a wait: the worker stamps `progress_unix` from it only there.
- **Why a dev check ticks.** Between two waits a dev check generates 1,800 programs, a few minutes of GPU work with no wait to heartbeat. `dev_tick`, called after every generation batch (`scratchcoder.rl.dev.ticking_generations`, the same batches as `generate_many`), stamps the GPU activity and refreshes the heartbeat, as `tick` does for the evaluation files; it enforces no limit, since the margin was kept before the update and the check's wait is checked before it starts.
- **Why the watchdog's extension is bounded by kind.** The Pod's own timeout ends every wait, so a longer idle GPU than that plus a slack means a hung worker, whatever its heartbeat says. A run-1 policy has no extension at all.
- **Why a channel stop ends the run.** The control's dev checks need the same Mac, and a Mac that timed out, lost its sandbox or vanished is a problem for a person. The evaluation of a half-run arm would also be spent on a comparison that cannot be made.
- **Why each check's weights go up at once.** A Pod deleted mid-run (a dead Mac, the timer) must not take the only copy of a check that may win the selection.
- **Mistake to avoid: a wait that cannot end in time.** `should_stop` is not read during a wait, so a wait started near the cost stop would run past it. The worker refuses to start one (`wait_margin`).

## Questions and answers

1. *Why does the probe-stopped run still publish `r2_final`?* Every label it made (the probe) verified in R2, so the supervisor can verify the stopped run's report and artifacts and approve teardown without a grace period.
2. *What happens if the SFT weights never reach R2?* The run fails `r2_milestones_unverified`; the supervisor pulls `exports/sft-weights/` over SSH with the verified pull, checks its SHA-256 and only then approves teardown.
3. *Why is the projection priced at the token caps?* Pool attempts that stop early only make the run shorter; pricing at the cap makes the rule an upper bound.
4. *Can an export be scored by mistake?* No: its placeholders are recognized and refused, and each one hashes the hidden test it replaced, so only the matching full file is accepted.
5. *What does run 2 add?* RL and more-SFT stage kinds over the reward bridge, the `awaiting_rewards` heartbeat with the watchdog's bounded extension, the lease as in-Pod progress during a wait, the lost-bridge and margin stops, and the bridge directories as a final label.
6. *What happens if the Mac's bridge process dies but the Mac does not?* The lease goes stale; the owner restarts the same `rl-bridge` command over the same `--state`, which takes its lease back at once and replays any stored reply. Restarted within 600 s of its last renewal, the run continues; later, the worker ends it as `bridge_lost`.
7. *Why does the smoke script its programs?* A 1-layer random model writes no closed python block, so no dev check would cross the bridge and every reward would be 0. The model still generates as usual; only the completion is replaced, by a correct or an off-by-one program for its task.
