# Rehearsal run worker

`tools/rehearsal_run.py` trains one of the two rehearsal runs on a single A40 Pod that already exists. Run A trains `stage1` on English web text, then `stage2` on Python plus unseen English. Run B trains one `mixed` stage on all three streams. Both start from the same saved initialization and read exactly the same documents, each exactly once. The worker never creates, rents or deletes a machine. Checkpoints leave the Pod through R2 while training continues. The Mac-side tools watch the heartbeat and delete the Pod.

The two specifications are [configs/rehearsal-a40-s-a.json](../../configs/rehearsal-a40-s-a.json) and [configs/rehearsal-a40-s-b.json](../../configs/rehearsal-a40-s-b.json). They hold the owner-approved values of decision D-35.

## Worked example

**Tiny smoke.** `python -m tools.rehearsal_run smoke --output runs/rehearsal-smoke` writes authored shards for every bound stream. It writes one seed-0 initialization and trains both runs on CPU against an in-memory bucket. The tiny model packs 8-token windows, 2 per microbatch and 2 microbatches per update, so one update holds 32 targets. Run A's `stage1` has 254 targets: `ceil(254 / 8) = 32` windows and `ceil(32 / 4) = 8` updates. The last update holds `254 - 7 x 32 = 30` real targets; the rest of it is padding. `stage2` adds 216 targets in 7 updates, numbered 9 to 15. Run B's single stage holds all 470 targets in 15 updates. With a validation interval of 4, run A validates its subset at global updates 0, 4 and 8 in `stage1` and at 12 in `stage2`. It validates both full streams at each quarter of a stage, the stage updates `round(k x updates / 4)` for k = 1, 2, 3, and at each stage end: `stage1`'s quarters are its updates 2, 4 and 6, `stage2`'s are its updates `round(1.75) = 2`, `round(3.5) = 4` and `round(5.25) = 5`, so run A validates fully at global updates 2, 4, 6, 8 and 10, 12, 13, 15. Run B validates its subset at 0, 4, 8 and 12, and fully at 4, 8, 11 and 15. The smoke prints both runs' multiset digests; they are equal.

**Real runs.** At the S packing an update holds 16 x 8 = 128 windows of 1,024 tokens (131,072 targets). Each of run A's stages has 10^9 targets, so 976,563 windows and 7,630 updates. Warmup is `round(0.02 x 7,630) = 153` updates. The final update holds 51 windows: 50 full ones and one with 512 targets. Run B has 2 x 10^9 targets in 15,259 updates with a 305-update warmup. Stage 1's first update uses `6e-4 / 153` and its last `6e-5`. Stage 2 restarts at `3e-4 / 153` with a fresh optimizer. Subset validation runs at global updates 0, 500, ..., 15,000: 31 times in each run. Run A's stage-2 validations start at 8,000, continuing its global count. Both full streams are validated at stage updates 1,908, 3,815 and 5,722 and at the end of each of run A's stages (global updates 1,908, 3,815, 5,722, 7,630, then 9,538, 11,445, 13,352, 15,260), and at 3,815, 7,630, 11,444 and 15,259 in run B: 8 full passes for A and 4 for B.

**Launch rule.** The plan is the whole run at the reference speed of 56,479 tokens a second: 2 x 10^9 targets take 35,411 s. Validation adds 1,598 s for A and 1,109 s for B at the planning rate of 100,000 tokens a second: 31 subsets of 2 x 10^6 targets plus 8 (A) or 4 (B) full passes of the binding's 12,220,020 targets, about 122 s each. Startup is 300 s per stage (600 s for A, 300 s for B). Checkpoints are one 15 s save per 1,800 s of training and validation plus one per stage end: 22 saves (330 s) for A and 21 (315 s) for B. The finalization reserve is 900 s. In total A needs 38,839 s and B 38,035 s. The worker refuses to start unless that much Pod lifetime is left, and the receipt tool refuses to write a receipt on the same rule (`launch_fit`, `require_fit`). The lifetime ends at the first of the 45,000 s wall, the armed in-Pod deadline, the watchdog's wall and either cost stop (`lifetime_end`). With the deadline armed 180 s inside the wall, Pod setup may take up to 5,981 s (100 minutes) for A and 6,785 s (113 minutes) for B. At the 90% floor the same plan would need 42,804 s and 42,000 s, which fit when Pod setup takes at most 2,016 s (A) or 2,820 s (B); a run that cannot finish is the 900 s check's business, not the launch gate's.

## Data flow and shapes

1. **Launch gates (`run`).** The worker accepts exactly the receipt `python -m tools.pilot_readiness_receipt rehearsal` writes (`check_readiness`):
   - `kind` is `rehearsal-readiness` and `run` is this specification's run;
   - the specification, the binding, the preflight report and the initialization are bound by SHA-256, and none of the four is optional;
   - every gate in `REHEARSAL_GATES` (`rehearsal_ops.READINESS_GATES`, the receipt builder's own names) is `true`: the pilot's applicable gates, `pod_self_destruct_armed`, and `r2_round_trip_tested`, `r2_shards_staged_and_hash_checked` and `r2_token_bucket_scoped`;
   - `revision` is `{"git_commit": <40 hex digits>, "clean": true, "archive_sha256": <64 hex digits>}`, and the `--revision` file (by default `/workspace/rehearsal/revision.json`, shipped by the runbook from the Mac) equals it exactly (`check_revision`). The Pod's copy of the code is a `git archive` without `.git`, so `git_commit` and `dirty` in the report say `null` and `true`; `code_revision` in `report.json` is the record of the commit that trained.

   The pilot's `ssh_transfer_tested` is not required, because checkpoints leave through R2. The termination guarantee, Pod identity, watchdog policy and armed deadline are checked by the same helpers as the pilot's. The policy must say `mode: rehearsal` and carry this specification's `max_transfer_seconds`. The specification's `rolling_skip_seconds` must be at least 900 (`ROLLING_SKIP_SECONDS`). The Pod ID comes from the receipt's captured identity, because the worker's SSH launch does not source `/etc/rp_environment`; `RUNPOD_POD_ID`, when set, must match it, and `r2_run_prefix` must be this Pod's prefix. Then the launch rule above. The A40 preflight must have passed its precision, resume, fused-attention and compile checks (`tools.pilot_preflight --compile-check`). R2 credentials come from `R2_ENDPOINT`, `R2_BUCKET`, `R2_POD_ACCESS_KEY_ID` and `R2_POD_SECRET_ACCESS_KEY`.
2. **Data.** `load_run_data` calls `rehearsal_binding.verify_binding` for the run. That re-hashes every shard, manifest and the tokenizer, and recomputes each stage's document order. The specification's packing and planned updates must equal the binding's. The initialization must hash to `--initialization-sha256` and be in the parent-checkpoint format `{"config": {"model": ...}, "tokenizer_hash", "model", "run_id": "rehearsal-init"}`.
3. **Each stage.**
   - The parent's bytes are hashed against the SHA-256 recorded when it was saved: the initialization for stage 1, stage 1's `final.pt` for stage 2.
   - A `OnePassLoader` over the stage's shards emits microbatches of `[16, 1024]` inputs and targets.
   - A `Trainer` loads the parent's weights only, with a fresh AdamW and a cosine schedule with its own warmup. `torch.compile` is on.
   - After each update the worker appends a row to `updates.jsonl` and writes the heartbeat.
   - At every multiple of 500 global updates it validates the fixed subset: the first 1,000,000 targets of each validation stream, cut into document windows of at most 1,025 tokens. Batches hold 8 windows with bfloat16 autocast; logits are `[8, <=1024, 65536]`.
   - At stage updates `round(k x updates / 4)` for k = 1, 2, 3 (`quarter_updates`) it validates both full streams. The stage record lists the planned updates (`planned_quarter_updates`) and each result (`quarter_validations`: the quarter, the stage and global update, both streams and the seconds).
   - Every 1,800 s it saves a rolling checkpoint, except near the stage end: when the stage's remaining updates at its measured seconds per update (the reference speed before any update), or the training deadline, end within `rolling_skip_seconds` (900 s), no rolling save starts, and the stage record notes the first skipped update (`rolling_saves_skipped_from_update`). A rolling upload therefore never sits ahead of the stage-final milestone.
   - At the stage end it compares the loader's ticket with the binding's: documents, targets, windows, updates, multiset and order digests. It saves the milestone, then validates both full streams (`full_validation`).
4. **Checkpoints.** Each save writes `checkpoints/<stage>/last.pt` (rolling) or `final.pt` (milestone). It then publishes `exports/<label>/` with `checkpoint.pt` (a hard link), `checkpoint.pt.sha256`, `record.json` (the report so far), `updates.jsonl` (all rows so far) and, for milestones, `ticket.json`. The directory is submitted to `CheckpointUploader` under `rehearsal-runs/<run>/<pod id>/<label>/`. Labels are `<stage>-step<global update>` and `<stage>-final`. The uploader keeps the two newest rolling labels and every milestone. A milestone submission drops any rolling label still waiting to start that was first submitted before it; resubmitting an older milestone keeps the newer rolling labels. A milestone that fails to upload, or that the cost cap refuses, is uploaded again for the rest of the run, 15 s after its first failure and then doubling up to 60 s; due milestones go before rolling labels. Older local rolling directories are removed once the uploader no longer needs them; milestone directories are never removed.
5. **Finalization.**
   - The heartbeat reads `uploading` from here until the last step, whatever the training outcome, so it reads `uploading` while any milestone is still pending or in flight. The GPU is idle. The watchdog allows this for the policy's `max_transfer_seconds` (900 s) after the last GPU work; past its 600 s idle limit, only while the Mac sees progress (new objects in R2, or an SSH pull's bytes growing). The final save counts as GPU work, so the window starts with finalization.
   - The window is split three ways. The worker's final heartbeat is due at the **handover**, `PULL_RESERVE_SECONDS` (420 s) before the window ends: 480 s after the last GPU work, before the idle limit, never past the Pod end less a minute (`handover_due`). The rest belongs to the Mac supervisor's SSH pull of any milestone R2 did not take.
   - The worker resubmits every milestone the uploader has not verified (one waiting out its backoff becomes due at once) and drains the uploader until `FINALIZE_MARGIN_SECONDS` (120 s) before the handover: 360 s after the last GPU work for a normal ending (`drain_budget`).
   - It checks every milestone in R2 by HEAD against the digests it sent, the newest first. A milestone that fails this check is resubmitted and drained again, at most three rounds in all (`settle`).
   - It writes `report.json`, uploads it to `rehearsal-runs/<run>/<pod id>/report.json` and checks that too. Only then are the rolling labels checked, for the record: no ending depends on them. They are checked after a failed `report.json` upload too, while time lasts (`record_rolling`).
   - Every R2 call after the drain goes through `_checked`: it retries transient failures up to `CHECK_ATTEMPTS` (6) times while time lasts, each attempt with a single-attempt `r2_store.bounded_store` whose socket timeout is at most `CHECK_TIMEOUT_SECONDS` (20 s) and a quarter of the time left until `FINAL_WRITE_SECONDS` (10 s) before the handover, so an endpoint with up to four addresses still answers or fails in time. No call starts within `LAST_CALL_SECONDS` (45 s) of the handover, except the HEAD that verifies a `report.json` PUT that succeeded, which may start until the final writes; one that cannot start raises `HandoverDue`, a `TimeoutError`. A milestone HEAD that cannot start in time leaves its label unverified, and a rolling label's leaves it unchecked (`labels_unchecked`), since R2 may still hold it whole; a `report.json` upload that cannot leaves the run `failed`. Either way the final heartbeat is not late: closing the uploader waits at most 5 s of the last 10.
   - Only then does the heartbeat read its final status. A completed or time-limited run whose milestones are all verified reads `awaiting_transfer`, with `r2_final`: the report key and SHA-256 and the final checkpoint's key and SHA-256. `r2_final` always names the last stage-final milestone, never a rolling label, and it is published for a stopped run too when that milestone and every earlier one are verified.
   - If any milestone is still unverified at the handover, the run ends `failed` with `failure: r2_milestones_unverified` and `training_status` set to how training ended, and gets no `r2_final`. `finalization.json` and `report.json` (`r2.unverified_milestones`) list each such milestone: its `label`, `export` (`exports/<label>`), absolute `export_path`, `checkpoint_sha256` and `checkpoint_size_bytes`, and every file's `name`, `path`, `sha256` and `size_bytes`. The supervisor pulls those exports over SSH instead of approving teardown.
   - Every heartbeat carries the Pod ID (`pod_id`), and the final one carries `failure` when there is one. `finalization.json` records the drain budget, each resubmission round, every check (`labels_verified`, and `labels_unchecked` for rolling labels with no time left), the transfer window's end, the handover time and any HEAD errors. A wall or cost stop skips all of this and reads `stopped` at once.

## Design choices and common mistakes

- **One stage end is not run completion.** The heartbeat reads `running` through every stage and across run A's boundary, then `uploading` during finalization. Every label's `record.json` also says `running`. A completed or time-limited run reads `awaiting_transfer` only once every milestone and `report.json` are verified in R2. If a milestone cannot be verified, the run ends `failed` (`r2_milestones_unverified`) with the local exports listed, and the supervisor copies them over SSH before any teardown.
- **A milestone is never given up during the run.** R2 may refuse or drop uploads for minutes. A failed milestone is retried for the rest of the run, and finalization resubmits it at once rather than waiting out the backoff. Retention never deletes a milestone, and the local export stays until the Pod is gone.
- **Rolling saves stop before the stage end.** Without that rule a rolling save one update before the end would upload first and the milestone would wait behind it, possibly past the transfer window. The only cost is that the newest rolling checkpoint may be up to 900 s older when the milestone is saved.
- **Every planned stage is in the report.** A stage that never started is listed as `pending` with no final checkpoint. The Mac side reads the stages with a final checkpoint as the closed ones, so a run A time-limited between its stages closes at `stage1-final`, but only a run that closed every stage counts as completed.
- **Global numbering.** Run A's stage 2 continues the global update count. Its trainer still numbers its own steps from 1, so its learning-rate schedule and warmup restart; its quarters are counted in its own updates.
- **Verify before trusting a parent.** The trainer reads its parent by path. Hashing the file first means a corrupted stage-1 checkpoint stops the run before stage 2 rather than training from it.
- **Post-compile speed, then fit.** At 900 s the speed check measures throughput, leaving out each stage's first two updates, which carry compilation. A run below 90% of 56,479 tokens a second stops (`throughput_below_limit`). So does a run whose projected finish passes the Pod end, the armed deadline when that comes first (`projected_finish_after_deadline`); this rule binds even when the speed passes. The projection adds, at measured rates, the remaining targets, every remaining validation (the subsets and each later quarter and stage-end full pass), a recompilation per later stage, the remaining checkpoint saves and the 900 s reserve. No save has happened by 900 s, so each save counts at the planned `checkpoint_save_seconds` (15 s) until one is measured. The report records the rule (`speed_check.rule`) next to the launch rule (`launch_fit.rule`); the launch rule, the receipt's `time_fit` and the projection count the same validations.
- **The reserve permits finishing, not training.** Training stops when only the 900 s reserve is left. The current stage still gets its milestone save and uploads, but no further quarter or stage-end full validation and no next stage, and the run ends `time_limited`. The wall, cost (`$10.00`) and idle (600 s) limits are never extended. A wall or cost stop does not even wait for uploads.
- **Stops as in the pilot.** Twenty-five consecutive rising losses and the speed check end a run `stopped`. A nonfinite loss or metric ends it `failed`.
- **Records stay small and secret-free.** `report.json` must stay under 1,000,000 bytes; per-update rows live in `updates.jsonl`, and the uploader keeps only its newest 100 failures and refusals (with a total count). Everything written goes through `sanitize` and then has every known credential value replaced, the R2 key pair included. An R2 error that echoes the key ID is redacted. Credentials never enter the Runpod create body or any argument.
- **Validation batches pad little.** The subset windows are sorted by length once. The full streams are sorted in runs of 512 windows. Only the batching changes; every window is still scored once.
- **Planning numbers.** `validation_tokens_per_second`, `startup_seconds` and `checkpoint_save_seconds` are planning bounds, not measurements. The speed check replaces the validation rate and the save time with measured ones. `max_transfer_seconds` must equal the watchdog policy's; the receipt tool and the worker both check it. The drain is not a planning number: it is what is left of that window before the checks and the SSH-pull reserve, at most 360 s.
- **Key order.** The specification's validation streams are read in the binding's order whatever the JSON file's key order, so a file rewritten with sorted keys means the same run (its SHA-256 still changes, and the receipt binds the bytes).
- **Not covered.** There is no resume after a crash: a failed run keeps its R2 labels and stops. A CPU smoke says nothing about A40 speed, memory, bfloat16 behavior or R2 throughput.

## Verification

Implementation: [`tools/rehearsal_run.py`](../../tools/rehearsal_run.py) and the uploader in [`tools/r2_store.py`](../../tools/r2_store.py); the compile check is in [`tools/pilot_preflight.py`](../../tools/pilot_preflight.py). Reference tests: [`tests/test_rehearsal_run.py`](../../tests/test_rehearsal_run.py), run with:

```sh
uv run --locked pytest tests/test_rehearsal_run.py tests/test_rehearsal_integration.py tests/test_rehearsal_readiness.py tests/test_r2_uploader.py tests/test_r2_store.py
uv run --locked python -m tools.rehearsal_run smoke --output runs/rehearsal-smoke
```

The tests run both runs on authored shards with a fake clock and an in-memory bucket that answers HEAD and GET as R2 does. They check:

- the approved values in both specifications, the launch rule's arithmetic at the reference speed (quarter passes included) and the strict schema;
- that a receipt built by the receipt tool is accepted by `check_readiness` and the `run` command line, and that a tampered specification, binding, preflight or initialization hash, another run's receipt, a wrong transfer window, R2 prefix or rolling-skip window is refused;
- that `run` refuses a missing, different or dirty code revision before creating any output, and records a matching one as `code_revision`;
- the smoke's heartbeats, reports and bucket replayed into the real supervisor, which tears down only after verifying R2, and never on a mismatched SHA-256;
- the final drain's budget, the handover 420 s before the transfer window ends, checks after the drain that stop in time (the newest milestone checked first) with the uploader's close taking its whole timeout, rolling labels checked or named unchecked after a failed `report.json` upload, and the `uploading` heartbeat with no GPU activity;
- a milestone that fails during training and is retried until it verifies; one resubmitted at finalization instead of waiting out its backoff; and one that never verifies, which ends the run `failed` (`r2_milestones_unverified`) with its export, files and SHA-256s listed, for stage 1, the final stage and a stopped run;
- that rolling saves stop when the stage's measured remaining time or the training deadline falls within the skip window;
- the stage transition: the parent hash, a fresh optimizer, a new peak and warmup, and a refused tampered stage-1 checkpoint;
- exact one-pass exhaustion with the masked final update;
- the global validation cadence and full validation at each quarter and stage end;
- rolling and milestone labels in the bucket, retention and local pruning;
- that A's two stage multisets combine to B's and both equal the bound value;
- the speed-check abort paths and its post-compile exclusion;
- the cost, wall, idle, rising-loss, nonfinite and reserve stops;
- the heartbeat across the stage boundary, its Pod ID, and `awaiting_transfer` only after R2 verification;
- the report size bound, and that no credential value reaches any file or object.

They also check the readiness and preflight gates, the shared initialization, and the glue between a verified binding and the worker.

## Questions and answers

1. *Why can run A's two stages be compared with run B at all?* Both runs start from the same saved initialization, and their tickets prove they read the same token multiset. The comparison still differs in the stage-2 optimizer and schedule reset, so it is a recipe comparison, not an order-only one.
2. *Why does the heartbeat not read `awaiting_transfer` as soon as training ends?* The Mac side deletes the Pod on that status. Until the milestones and the report are verified in R2, the Pod still holds the only copy. Meanwhile it reads `uploading`, which keeps the idle Pod alive for the transfer window only while the Mac sees the uploads arrive.
3. *What happens if training is slower than planned?* The launch rule needs the whole run to fit at the reference speed. The 900 s check then stops a run below the speed floor, or one projected to pass the deadline at its measured speed, while little money is spent. A run that slows later stops at the reserve with a time-limited milestone.
4. *Why hash the stage-1 checkpoint again before stage 2?* The trainer loads its parent by path. A file changed after its save must not become the starting weights.
5. *Why is validation every 500 global updates, not every 500 stage updates?* Global numbering puts run A's and run B's validations at the same token counts, so their curves line up. The full passes follow the approved plan instead: each quarter of every stage, so both of A's stages and B's single stage are measured at the same fractions of their own schedules.
6. *What if R2 never accepts a milestone?* The run ends `failed` with the milestone's local export listed. The supervisor copies it over SSH and checks its SHA-256 before it lets the Pod go; the watchdog's wall, cost and transfer limits still bound the Pod if that copy fails too.
