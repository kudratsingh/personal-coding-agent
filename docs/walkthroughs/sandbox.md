# Isolated execution boundary

The host serializes candidate code, tests, and limits as data. It starts a fixed hardened Docker command and passes that JSON through standard input. No repository directory, secret, or daemon socket is mounted in the container. All candidate execution occurs under `scratchcoder.sandbox` inside the container.

A trusted container supervisor writes the candidate into its temporary filesystem and starts a child interpreter with a small explicit environment. Function tests require actual completion after assertions; I/O tests compare captured output for supplied input cases. A bounded reader enforces output limits, and process/container limits contain resource abuse. Host timeout cleanup removes the exact run container.

The supervisor runs as PID 1 under the candidate's own unprivileged user, so before any candidate exists it protects itself, as the reward supervisor does. It gives the catchable signals (`SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`, `SIGUSR1`, `SIGUSR2`) a no-op handler; a pid-namespace init never receives the other signals, `SIGKILL` included. It also calls `prctl(PR_SET_DUMPABLE, 0)` and checks the result with `PR_GET_DUMPABLE`, so the kernel refuses a same-user process access to `/proc/1/mem` (where the expected I/O outputs and the result nonce live) and `/proc/1/fd/1` (the result channel). If either protection cannot be established, the supervisor runs nothing and reports `unprotected`. The candidate's source is written to `/tmp/candidate.py` once, before any candidate runs, with `O_EXCL` and `O_NOFOLLOW`, and never reopened: `/tmp` is writable by the candidate, and a rewrite between I/O cases could follow a planted symlink to `/proc/1/fd/1` (which PID 1 itself may open) or block on a FIFO. After every case the supervisor kills every other process in the container, so nothing one case leaves running reaches the next.

The host accepts exactly one ASCII result line, ending in a newline, that carries the random nonce it sent, the expected fields and types, and both protections reported as held. Anything else is an `infrastructure_error` with a `detail` (`malformed_response`, `supervisor_unprotected`, `spawn_failed`, or `runner_error` for a host-side exception of any type). That status is never a verdict: the harness refuses to report a score, and the executor retries it and then leaves it `unresolved`. A failure before the first candidate process starts is `spawn_failed`, a host failure; a failure after that is the candidate's (for example, its leftover processes holding the pid limit). Conformance run 2 showed what these protections close: before them, an I/O candidate read every expected output from `/proc/1/mem`, and a candidate's write to `/proc/1/fd/1` made the host fail to parse the result and stop the evaluation.

Function mode still decides its verdict inside the candidate's process (the tests and the completion marker share it), so a candidate can forge that verdict. This is an unresolved scorer-integrity limitation of every function-mode score in use now, described in the [conformance walkthrough](evaluator-conformance.md#demonstrated-limitations-observed-in-the-local-gated-runs).

For an infinite loop, the supervisor reaches the wall deadline and kills the child. If the whole container is killed by its memory limit, the host reports a resource failure. Neither path grants a passing result or falls back to host Python.

See [ADR 0004](../adr/0004-development-sandbox.md) for the threat boundary and grading limitations. Integration tests run only when explicitly enabled on a disposable Docker worker; absence of the daemon is not a passed security test.

Reinforcement-learning rewards use a different supervisor through the same hardened command, described in the [reward-channel walkthrough](reward-channel.md): the host keeps the expected values and sends only each hidden assertion's call (or each I/O case's input) into the container, so a candidate cannot forge a pass, and host failures are reported distinctly from candidate outcomes so they are retried rather than scored. That path leaves this one, the evaluation path of record, unchanged.

Questions: why no bind mounts (deny host files); why fixed local daemon (avoid remote paid resources); why bound capture twice (protect supervisor and host); why kill the container (contain surviving descendants); why refuse a host fallback (preserve the isolation contract); why fail closed without the protections (an unprotected supervisor's verdicts can be forged); why a nonce on the result line (a stray or injected line is never mistaken for the result); why keep malformed output unresolved rather than failed (a candidate that cannot reach the result channel cannot cause it).
