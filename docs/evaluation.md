# Evaluation policy

The initial external reference-model result is available but does not reproduce its published comparison score; see [reference evaluation](reference-evaluation.md). No result from a real-corpus-trained project checkpoint is available. Reports must identify checkpoint, source/dataset revision, split, decoding settings, seed, execution limits, and metric definition.

Report uncertainty across tasks or seeds as appropriate, and include negative results. Compare checkpoints on the same task set and settings; distinguish development tuning from held-out reporting.

Validate the harness against simple known answers and a reference baseline before trusting model scores. Generated code must run through the isolated runner, with hidden tests kept out of model-visible feedback.

The planned scorecard compares pretraining stages, supervised tuning, test-based optimization, and the repair loop. Scorecard rows will be added when supported by reproducible evidence.

The metric implementation includes unbiased pass@k, equal-task-weighted mean pass rate, aligned-answer accuracy, bits per byte, and paired task bootstrap intervals. Exhaustive small-subset tests and hand-computed fixtures validate the formulas. These correctness checks are not benchmark scores.

`scratchcoder eval --help` documents local checkpoint evaluation against normalized held-out task JSONL. The harness records input/checkpoint/tokenizer hashes, source revision, dirty state, seeds, decoding settings, per-task outcome hashes, equal-task metrics, and source/authorship breakdowns. Completed reports and compact scorecard JSONL stay in ignored local outputs. Missing isolation aborts reporting; context overflow is recorded as a model limit, not silently truncated.

Code evaluation defaults to `--prompt-mode base`: tokenize the raw task prompt after `rstrip()`, apply the original reference stop strings to the decoded completion, and score stripped prompt plus retained completion without removing leading completion whitespace. Reports/scorecards record `prompt_stripped: true` and the exact `base-completion-rstrip-v1` protocol. This is intended for code-prefix completion tasks. The explicitly selected `--prompt-mode instruction` preserves the historical public-tests prompt and fence/entry-point heuristic, records `prompt_stripped: false`, and must not be mixed with base-completion results. Multiple-choice label scoring and canonical reference checks do not use this generation protocol and are unchanged.

Two post-training protocols are defined for the rehearsal. `scratchcoder eval` does not select them; the evaluation pipeline below does. **`chat-v1`** renders the pool task (prompt, a blank line, the public test) or the benchmark prompt as the user turn. It generates after `<|assistant_start|>` and scores the first closed python block; with no block, the attempt scores 0. **`base-pool-completion-v1`** puts a pool task's text and public test in a module docstring. It generates at most `min(512, 1,024 − prompt)` tokens and keeps the completion before the first stop string of the task's mode. Both modes stop at `\nassert`, `\n"""` and `\n# Test`; function-mode tasks also stop at `\nif __name__` and `\nprint(`. Its record lists the stops per mode under `stop_strings_by_mode`, and truncation takes the task's mode with no default. The protocol was amended on 2026-10-26, before its first scored use, to drop `\nprint(` for I/O tasks: a stdin/stdout program prints its answer at the top level, so that stop cut 8 of the 26 dev and 705 of the 1,514 train I/O reference solutions, and after the amendment no stop cuts any of them. A second amendment the same day also dropped `\nif __name__` for I/O tasks, because a base model's `if __name__ == "__main__": main()` would otherwise be cut before the call; no reference I/O solution contains such a line. The name stays `base-pool-completion-v1` because no scored run used the earlier stops; the stop table is part of the protocol record, so the record's SHA-256 changed. Both strip the task text and public test with `strip()`, so their records say `prompt_stripped: true` and name the rule in `prompt_strip`. Base-versus-chat comparisons are cross-protocol, on the pool and on the benchmarks: chat-v1 scores the extracted block alone, without the benchmark prompt's imports and helpers. See the [chat-v1 walkthrough](walkthroughs/chat-format.md).

Sampled decoding (temperature above 0) uses the counter-based sampler `philox4x32-10-inverse-cdf-v1`: each attempt's uniforms come from its harness seed and the step number, so a seeded attempt draws the same random numbers alone or in any batch. Its logits can still differ by float rounding between batch shapes (batch size and prefill chunk size), so its tokens are identical up to that rounding, not exactly. CPU tests see identical tokens; this is not verified on a GPU. Reports of sampled runs record `sampler_version`; greedy reports are unchanged. Seeded draws from the earlier `torch.multinomial` sampler are not reproduced, and no result of record used sampled decoding. See the [generation walkthrough](walkthroughs/kv-cache.md).

`scratchcoder generation-benchmark` measures generation speed only. It builds the model from `--checkpoint` with `--tokenizer`, or from `--config` (a YAML or JSON file with a `model` mapping) with seeded random weights. It then times batched generation at each `--batch-sizes` value (default 1, 64, 128, 256) on synthetic random-token prompts whose lengths cycle through `--prompt-lengths` (default 190), with `--max-new-tokens`, `--temperature`, `--top-k` and `--top-p`. `--device` takes `cpu`, `cuda` or `cuda:N` with no fallback, and `--precision bfloat16` selects autocast. The command prints JSON: generated tokens per second (prefill included), prefill time, peak memory (CUDA allocator peak, or process peak resident memory on CPU), device, precision and sampler version. No stop tokens are used, so every row spends its whole budget. Each batch is one `generate_batch` call, left-padded to its longest prompt: with mixed lengths it is one unsorted batch, padded more than the length-sorted batches of `generate_many`, and each result records `prompt_slots` (batch size times the longest prompt) and `prompt_padding_fraction`. To time a sorted batch, give lengths from one batch of the sorted pool. It runs no generated code, writes no files and provisions nothing.

Function tests and I/O cases use the same isolated runner. An I/O call's deadline is the pool verification's rule, 2 s plus 0.25 s per case, at most 60 s, because each case starts a fresh interpreter and every dev I/O task has 99 hidden cases; a function call keeps 2 s. A call the host watchdog ended (`host_stalled`) is retried up to three times and never scored; if it persists, `scratchcoder eval` aborts. Public prompts exclude hidden tests and reference solutions. A dedicated disposable CI integration test verifies a known correct and incorrect synthetic candidate through the real runner, pool admission, metrics, and scorecard. This is not a reproduction of an external model's benchmark score.

`scratchcoder eval-choice` evaluates explicit local held-out multiple-choice JSONL with checkpoint label likelihoods, accuracy, and task-bootstrap intervals. See the [multiple-choice walkthrough](walkthroughs/multiple-choice.md) for the exact prompt, scoring policy, reference tests, and data schema. The [ARC-Easy guide](arc-easy.md) records verified complete held-out intake and the synthetic-only nano run, including every context-limit failure in its denominator.

`scratchcoder eval-validation` records per-domain held-out loss/bits per byte from an explicit local checkpoint, tokenizer, and domain-to-shard JSON map. Supply `--documents` as the maximum first-document-prefix windows per domain; optional `--sequence-length` defaults to model context. Reports identify this bounded, nonrandom diagnostic protocol, actual/available document counts, source/checkpoint/tokenizer hashes, and metrics. It is not a full-corpus estimate. Byte counts use raw token bytes, not replacement-character decoding. See [training validation](walkthroughs/training-loop.md) for the metric reference and denominator convention. No dataset is downloaded, no training occurs, and no code is executed.

The [EvalPlus workflow](evalplus.md) preserves pinned official standalone test scripts and requires a complete canonical preflight before optional checkpoint scoring. Reported runtime/limits are explicit, not claimed equivalent to official per-input resource calibration. Safe failure categories do not include raw stdout, test source or tracebacks. Benchmark defects or inadequate resource limits must be investigated rather than silently weakening tests or dropping tasks.

Observational failure categories additionally distinguish allowlisted dependency/import errors and common attribute/index/key/value/recursion/runtime errors. Only the fixed family label is returned, never its message or module name; unknown text remains `other_failure`. These labels are extracted heuristically from untrusted output and can be spoofed, so they are debugging hints, not an authenticated exception channel or acceptance criterion. Existing status/signal handling and test pass/fail decisions do not change. A missing dependency under a stdlib-only profile is not proof of mathematical incorrectness or permission to change that profile.

## Post-training evaluation pipeline

Generation and execution are separate steps joined by a hashed completions file; see the [pipeline walkthrough](walkthroughs/evaluation-pipeline.md) for the formats and the reasoning.

- **`scratchcoder eval-generate`:** writes one completions file. It takes `--checkpoint`, `--tokenizer`, `--suite` (`pool`, `humaneval`, `humaneval-plus` or `mbpp-plus`), `--split` (`dev` or `test` for the pool), `--tasks` (the pool JSONL or the pinned release), `--protocol` and `--output`. It also accepts `--device` (`cpu`, `cuda`, `cuda:N` or `mps`, with no fallback), `--precision float32|bfloat16` and `--batch-size`. Decoding is greedy by default, or `--samples N` with `--temperature`, `--top-p`, `--top-k` and `--seed`; each attempt's seed is the harness formula.
  - **Protocols:** `chat-v1` for every suite, `base-pool-completion-v1` for the pool and `base-completion-rstrip-v1` for the benchmarks.
  - **Budgets:** `min(512, 1,024 − prompt)` for chat-v1 and the base pool protocol, 256 for the base benchmark protocol.
  - **HumanEval+:** always excludes task 32, and every file records the exclusion.
  - **MPS:** greedy decoding only. The seeded sampler works in float64, which MPS lacks, so sampling on `mps` is refused before anything loads; use `cpu` or `cuda` for sampled files.
  - **Output:** the file's SHA-256 is printed, and the file runs no code.
- **`scratchcoder eval-execute`:** executes a pool completions file through the evaluation runner, with `--workers` (default 8) and `--tokenizer` (required for chat-v1, whose extraction reads token IDs, and for the test split, so its one read is never spent on unverified completions).
  - **Scoring:** host failures, including `host_stalled` results, are retried three times with bounded backoff and never scored. An attempt still failing is listed as unresolved. Every passing attempt records the reward channel's static audit.
  - **Results file:** append-only, keyed by task and sample, and named by the completions SHA-256. Running it again continues an interrupted run, but only under the execution environment it started under: the runner and supervisor sources, the image and the deadline rule must match the results header, or the run is refused. The command exits with status 3 while any attempt is unresolved.
- **`scratchcoder eval-seal`:** records a pool test completions file's SHA-256 in a hash-chained seal ledger. A head record, `<ledger>.head`, beside it names the event count and last hash, so removing the ledger's last events, or the ledger or its head record, is refused. Keep the two files together.
  - **Unsealing:** `eval-execute` refuses the test split unless given `--seal-ledger` and `--unseal`. The unseal record is a JSON file naming all four frozen endpoints' checkpoint SHA-256 values and the completions SHA-256 values to unseal.
  - **One read:** each test completions file is executed once, as a logged read that can resume after an interruption. A second execution is refused.
  - **No second look by regeneration:** one unseal record governs a ledger. Once any read has opened, no file can be sealed and every later read must present the same record, and a record may not list two files of one checkpoint, protocol and decoding (greedy or sampled).
  - **Refusals come first:** the ledger and the record are checked before the sealed task file is opened.
- **`scratchcoder eval-baseline`:** writes the constant-answer baseline of the pool dev split.
  - **Definition:** the reward channel's degenerate answers, best per task, reported as the mean best-constant reward and the share of tasks fully passed.
  - **Unparseable tasks:** constant-answer programs run through the runner. Tasks covered neither way are counted.
  - **Test split:** its baseline is computed only inside the first complete unseal read and recorded in the ledger.
- **`scratchcoder eval-test-baseline`:** the retry for a test-split baseline that the read could not log (a constant-answer call stayed unresolved, or the ledger write failed). It runs only after every completions file the unseal record lists has a completed read, under that same record and the task file those files name, and it exits with status 3 if the baseline is still not logged. A baseline already logged is returned unchanged.
- **Public benchmarks:** these run on GitHub Actions, through the manual `benchmark-score` workflow and `uv run --locked python -m tools.benchmark_dispatch` (run it as a module from the repository root; it imports its sibling `tools.r2_store`).
  - **Dispatch:** on the Mac, the tool checks a public-benchmark completions file against its R2 object and signs a GET link for that one object, expiring within an hour. It dispatches the workflow with `gh`, waits, downloads the `benchmark-results-<sha256>` artifact and checks that it names the same hash.
  - **Scoring:** the workflow downloads the file first and refuses another SHA-256. It runs the canonical preflight, then scores the attempts and every task's constant answers. HumanEval uses the reference gate's stdlib image; HumanEval+ and MBPP+ use the EvalPlus image and limits.
- **`scratchcoder scorecard`:** builds the scorecard from results files (`--results`), benchmark artifacts (`--benchmark`), `eval-choice` reports (`--arc`, with `--arc-tasks` for the labels) and baselines (`--pool-baseline`). Each checkpoint is named with `--checkpoint NAME=SHA256`. JSON goes to `--output`, with optional Markdown to `--markdown`. Each row reports:
  - greedy pass@1, or the n-sample mean pass rate and pass@n;
  - the suite's constant-answer baseline beside the score (for ARC-Easy, the best fixed answer position and chance);
  - pool slices by source and authorship;
  - unresolved counts;
  - GPU- and sandbox-minutes;
  - the checkpoint, tokenizer, task-file and protocol hashes and the precision.

  Named pairs (`--pair FIRST:SECOND`; by default SFT vs base, RL vs SFT, more-SFT vs SFT and RL vs more-SFT) get a paired task bootstrap with 2,000 resamples and seed 0, labelled cross-protocol when the protocols differ. Any checkpoint above 20% greedy pass@1 on HumanEval carries the leak flag. The flag is true, false or unknown: a checkpoint with no complete greedy HumanEval row is listed as not evaluated rather than clean.

No completions file, results file or scorecard has been produced for a trained checkpoint yet. The pool dev constant-answer baseline is 0.276 mean reward and 4.3% of tasks fully passed (1,995 of 2,000 tasks covered); the walkthrough gives it by source.
